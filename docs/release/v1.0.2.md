# v1.0.2 - Reads stay lock-free while a replaced value is held

`global-lib` 1.0.2 fixes a slow path in reads. No API change.

```toml
[dependencies]
global-lib = "1.0"
```

## What was wrong

When one thread was still reading a value (inside a `with` closure, for example) and another thread replaced it, the old snapshot had to stay alive until that read finished. While it did, every other read of the same `Global`, or every read by name for a store, since all names share one map snapshot, tried to free it: a lock attempt on the writer mutex, a scan of every thread's hazard record, and an allocation, after which it gave up because the snapshot was still in use. Reads were then neither lock-free nor allocation-free, and readers on every thread wrote the same mutex word.

## What changed

Only a reader that was reading a replaced snapshot tries to free it, when it finishes. Readers of the current value check that with one extra load and go straight back. The writer-side scan now checks the announcements in place, so it no longer allocates a list on every write either.

| Same machine, same job, three rounds | Before | After |
|---|---|---|
| `Global<u64>` read, nothing retired | 7.3 to 10.8 ns, 0 allocations | 6.9 to 12.3 ns, 0 allocations |
| `Global<u64>` read while another thread holds a replaced value | 71.7 to 86.9 ns, 1 allocation per read | 7.0 to 9.1 ns, 0 allocations |
| Read by name while another thread holds an old map | 94.2 to 95.8 ns, 1 allocation per read | 23.6 to 24.4 ns, 0 allocations |

A new test binary (`tests/alloc.rs`, with a counting allocator) fails on 1.0.1 and passes now, and a unit test checks that readers of the current value never attempt a reclaim while an old value is held, and that the holder frees it on the way out.

## Documentation

- A read that is still running when its value is replaced keeps that snapshot (for a store, the old map copy) alive until it returns, and the reader frees it, so the replaced value's `Drop` can run on that reader's thread.
- `set` stores exactly the type it is given: write `7000u16`, not `7000`, which is an `i32`.
